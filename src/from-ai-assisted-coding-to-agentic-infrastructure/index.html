From AI-assisted coding to agentic infrastructure

Why the future of software depends on intelligence built into the foundations of our systems

Munawar Abadullah · 25 October 2026 · 9 minute read

For years, software development was constrained by the time, expertise and resources required to turn an idea into a working application. AI-assisted coding is changing that equation. Developers can now generate code, explain unfamiliar systems, write tests and prototype applications at a speed that would have been difficult to imagine a decade ago.

But writing code faster is only one part of the transformation.

The more fundamental shift is the emergence of software systems that can understand context, communicate with other systems, coordinate tasks and take action. Over time, intelligence should become a foundational capability of the computing environment itself, rather than remaining confined to individual applications.

This is the broader vision behind agentic infrastructure: an intelligent layer that connects operating systems, applications, services, data and eventually robotics into a coordinated ecosystem.

Section 01When writing code stops being the primary bottleneck

Traditional software development places substantial value on the ability to translate requirements into working code. As AI coding tools improve, more of that work becomes accessible to people who are not traditional software engineers.

This does not make software engineering obsolete. It changes where engineering expertise creates the most value.

Architecture, security, data integrity, system integration, observability and operational reliability become even more important when generating code becomes easier.

An application that works in a demonstration is not necessarily a system that can safely operate in production.

The difficult questions remain:

  • Can the system access the correct data?
  • Can it execute actions securely and with appropriate permissions?
  • Can failures be detected, contained and recovered from?
  • Can its decisions and actions be audited?
  • Can it coordinate with other systems without losing context or creating conflicting outcomes?

These are not merely code-generation problems. They are architectural problems.

Section 02Intelligence should be a native capability, not an isolated feature

Much of today's AI adoption follows an application-first model. A company adds a chatbot to its website, integrates a model into a product, or introduces a copilot into an existing workflow.

These are useful applications, but they represent an intermediate stage.

My longer-term view is that intelligence should be built into the foundational layers of computing, including operating systems, application platforms, development environments, enterprise infrastructure and the systems that connect them.

Imagine an operating system in which intelligent capabilities are available to applications through consistent, secure interfaces. An application would not need to independently reinvent context management, model access, tool orchestration, or every basic intelligence-related capability.

A developer could build on a platform where these capabilities already exist, just as applications today build on operating-system services for files, networking, identity and process management.

The same principle applies beyond desktop and mobile operating systems. Enterprise platforms, cloud environments, industrial systems and robotics infrastructure could expose intelligence as a native service.

This does not mean that every component must contain a large AI model, or that every decision should be delegated to AI. It means the foundational architecture should be designed to make intelligence available wherever it is useful.

Intelligence should be a capability of the system, not merely a feature of the application.

Section 03Intelligence and compute should scale from low to high

A foundational intelligence layer should not depend on one model, one vendor, or one level of computing power.

Different tasks have different requirements. A simple classification, local search or device-control operation may need only a small, efficient model or a conventional deterministic function. A complex engineering problem or multi-system business decision may require a more capable model, additional context and greater compute resources.

A well-designed architecture should support this spectrum:

  • Lightweight intelligence: fast, low-cost capabilities running locally or close to the application.
  • Intermediate intelligence: more capable models handling complex interpretation, planning and coordination.
  • High-capability intelligence: powerful models and specialized compute for demanding reasoning, analysis and orchestration.
  • Coordinated intelligence: multiple specialized systems working together when a task exceeds the practical limits of a single model or process.

The architecture should choose the appropriate level based on the task, performance requirements, privacy constraints, reliability and cost.

Some workloads should remain entirely local. Others may use enterprise infrastructure or cloud-based models. Sensitive operations may need strict data boundaries, while less sensitive tasks can use broader resources.

The point is not to maximize compute for every request. It is to make intelligence available at the appropriate level, and to allow systems to move between levels when necessary.

This is where modularity becomes important. Intelligence services can be decoupled from individual applications while remaining natively accessible through well-defined interfaces.

A system should be able to use a different model or compute provider without requiring every connected application to be redesigned.

Section 04From non-intelligent systems to intelligent communication

Historically, software systems have communicated primarily through predefined APIs, databases, messages and integration rules.

These mechanisms remain essential. However, traditional integrations generally depend on developers explicitly defining what each system can exchange and how each interaction should be interpreted.

A system may expose thousands of data fields and endpoints without understanding the broader intention behind a request. Another system may contain the information needed to complete a task but lack a practical way to discover the relevant capability, interpret the available context, or coordinate an action.

The result is a fragmented environment in which people often become the integration layer. They move information between applications, reconcile conflicting outputs, and coordinate workflows that individual systems cannot manage together.

The next phase should move beyond simple connectivity toward intelligent interoperability.

Connected systems should be able to discover available capabilities, exchange structured context, communicate constraints, request actions, interpret results and coordinate work within explicit permissions.

Consider a business process involving a CRM, an accounting platform, a document repository and an analytics system.

Traditional integration can synchronize records between these platforms. An intelligent architecture could also coordinate a larger task: identify a customer request, retrieve relevant documents, check financial information, prepare a recommendation, and route the proposed action for approval.

Each system retains its own responsibilities and data boundaries. Intelligence coordinates the work across them.

This is a significant distinction. Connecting systems allows information to move. Intelligent communication allows systems to coordinate around an objective.

Section 05MCP is an important step, but the broader problem remains

The Model Context Protocol (MCP) is an important development in this direction. It provides a standardized way for AI applications to connect with external tools and data sources.

Instead of building a completely separate integration for every model and every tool, developers can use a common protocol to expose capabilities and provide context to AI applications.

This helps reduce integration friction and makes tools more reusable.

However, the broader vision extends beyond connecting a model to a tool.

We will also need effective ways for independent agents, applications, operating systems, enterprise services and physical devices to coordinate with one another. They may need to exchange task state, identify themselves, negotiate available capabilities, communicate constraints, request delegated work, and return verifiable results.

MCP can contribute to this ecosystem, but it should not be assumed to solve every communication requirement between autonomous systems. Different layers may require complementary protocols, additional standards, or new mechanisms as the architecture evolves.

The right approach is not to invent a new protocol simply because AI is involved. Existing technologies may already solve parts of the problem. The objective should be to identify the gaps and build interoperable standards where necessary.

The critical requirements are clear:

  • Common meaning: systems need structured ways to represent requests, context, capabilities and results.
  • Identity and trust: connected agents must be identifiable, and their authority must be verifiable.
  • Permission boundaries: a system must not gain unrestricted access merely because it can communicate with another system.
  • State and continuity: long-running tasks require mechanisms to preserve progress and handle interruptions.
  • Error handling: systems must be able to recognize failures, conflicting instructions and uncertain outcomes.
  • Observability: actions and exchanges need to be traceable and auditable.
  • Interoperability: different models, vendors, operating environments and hardware platforms should be able to participate without being locked into one implementation.

A protocol is only one part of the solution. The surrounding architecture must make communication meaningful, secure and reliable.

Section 06The same principle must eventually extend to robotics

This vision should not stop at software.

Robotics brings the physical world into the equation. Robots, sensors, machines, industrial controllers and autonomous devices need to communicate with software systems and with one another.

A robot operating in a warehouse, for example, may need to interpret a task, obtain inventory information, coordinate with other robots, respond to changing conditions, and report completion to an enterprise system.

That requires more than an intelligent model. It requires a coordinated architecture connecting perception, planning, physical control, operational systems and safety mechanisms.

The requirements are also different from those of ordinary software. Physical systems operate under real-time constraints, hardware limitations, environmental uncertainty and safety-critical conditions. Some decisions must remain local and deterministic rather than depending on a remote model.

The broader principle still applies: each component should have defined capabilities, and the system should have reliable ways to communicate, coordinate and manage responsibility.

Over time, common architectural principles could connect digital agents and physical agents into a larger ecosystem. The protocols will not necessarily be identical at every layer, but the systems should be able to cooperate through well-defined interfaces.

The opportunity is to move from isolated intelligent products toward environments in which intelligence can coordinate work across both digital and physical systems.

Section 07From copilots to autonomous workflows

An AI copilot primarily assists a human with a task. An agentic system can go further by pursuing a defined objective through a sequence of steps.

Depending on its design and permissions, an agent may interpret a request, develop a plan, retrieve information, call tools, execute an action, evaluate the result, and determine what to do next.

But autonomy is not the same as reliability.

An agent can make an incorrect assumption, call the wrong tool, repeat an action, encounter conflicting information, or lose track of its objective. Giving a model access to more tools does not automatically solve these problems.

A production-oriented agentic architecture needs several foundational capabilities:

Orchestration and state management: multi-step tasks require execution state, checkpoints, timeouts, retries and recovery mechanisms.

Identity and access control: agents should have defined identities and scoped permissions, with human approval for consequential actions where appropriate.

Tool and integration layers: systems need dependable interfaces to databases, APIs, enterprise applications and devices.

Memory and context: relevant information and task state must be available when needed, with appropriate separation between transient context, persistent memory and authoritative records.

Observability and evaluation: teams need visibility into tool calls, decisions, costs, failures and actual task outcomes.

Governance and safety: policy enforcement, audit trails, approval gates and limits on irreversible actions help keep autonomy within acceptable boundaries.

These capabilities form part of the infrastructure required to move from impressive demonstrations to dependable operations.

Section 08The competitive advantage will be the architecture

As AI models and coding tools become more accessible, access to intelligence alone becomes a weaker differentiator.

The advantage increasingly comes from how effectively an organization connects intelligence to its proprietary data, business rules, existing systems and operational processes.

Organizations that build reusable integration layers, secure execution environments, reliable orchestration and effective evaluation systems can deploy new intelligent workflows without rebuilding the entire foundation each time.

The same principle applies to operating systems and software platforms. If intelligence is treated as a collection of disconnected features, every application must solve many of the same problems independently. If the foundational platform provides common capabilities, developers can focus on the specific value their applications deliver.

The long-term opportunity is an ecosystem where intelligence is broadly available, compute can scale to the task, and systems can coordinate regardless of whether they were built by the same vendor or use the same underlying model.

That ecosystem will not emerge from models alone. It will require architecture, standards, engineering discipline and collaboration across the technology stack.

ConclusionBuild intelligence into the foundations

The evolution of software is moving beyond assistance with individual development tasks toward systems capable of coordinating work across applications, services and physical devices.

AI-assisted coding changes how software is created. Agentic infrastructure changes how software-enabled work is executed. A native intelligence layer changes how the entire computing environment can operate.

My vision is for intelligence to become a foundational capability across operating systems and software platforms, with the flexibility to scale from lightweight local processing to powerful models and coordinated compute. Those systems should remain modular, but they should also communicate intelligently through secure, interoperable interfaces.

MCP is one step toward that future. Further standards and complementary protocols may be needed to support coordination among agents, enterprise applications, operating systems and robotics.

The objective is not to put one giant AI in control of everything. It is to create a connected environment in which specialized systems can understand their roles, communicate effectively, collaborate on tasks and operate within clear boundaries.

The next major step in computing is not simply making every application intelligent. It is making intelligence a native capability of the system, and making systems intelligent enough to work together. That is the foundation on which agentic infrastructure should be built.
